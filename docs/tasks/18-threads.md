## Цель

Измерить, как программа масштабируется по потокам, и увидеть, что мешает ей масштабироваться: последовательная часть, память или когерентность кэшей.

## Что сделать

### 1. False sharing

Возьмите массив счетчиков, которые каждый поток обновляет независимо:

```c
#define N 8
long counters[N];

#pragma omp parallel for
for (int t = 0; t < N; t++)
    for (long i = 0; i < 100000000; i++)
        counters[t]++;
```

Замерьте время для 1, 2, 4, 8 потоков. Затем выровняйте каждый счетчик на отдельную кэш-линию:

```c
struct padded { long value; } __attribute__((aligned(64)));
struct padded counters[N];
```

Повторите. Объясните разницу: счетчики не пересекаются по данным, но лежат в одной линии, и ядро вынуждено согласовывать ее между кэшами.

### 2. Масштабирование суммы

Параллельте сумму большого массива:

```c
#pragma omp parallel for reduction(+:s)
for (long i = 0; i < n; i++)
    s += a[i];
```

Снимите время для 1, 2, 4, ... потоков (не больше числа ядер). Постройте график ускорения $S(p)$ и оцените долю последовательной части по закону Амдала:

$$
S(p) = \frac{1}{(1 - f) + f/p}
$$

### 3. Память против ядер

Повторите пункт 2 на массиве, который целиком помещается в L2, и на массиве в несколько гигабайт. В каком случае ускорение останавливается раньше и почему?

### 4. GEMM

Вернитесь к умножению матриц из задания 1 и распараллельте его по внешнему блочному циклу. Сравните ускорение с суммой и объясните, почему оно меньше.

## Синхронизация и NUMA

1. Сравните `pthread_mutex`, спинлок и `atomic_fetch_add` на счетчике: 4 потока, $10^7$ инкрементов. Объясните разницу.
2. Реализуйте SPSC ring buffer и замерьте пропускную способность (млн операций в секунду) при разных размерах буфера.
3. Запустите OpenMP-программу с `OMP_PROC_BIND=close` и без; на NUMA-машине сравните с `numactl --interleave`.
