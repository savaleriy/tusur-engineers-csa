# 7. Ветвления, косвенные вызовы и раскладка кода

!!! warning "WIP"
    Материал в работе: текст и задания могут меняться.

Процессор не ждет, пока станет известно, куда идет переход: он угадывает и выполняет код спекулятивно. Угадал - переход почти бесплатный. Не угадал - выбрасывает десятки инструкций. Значит, стоимость `if` зависит не от кода, а от данных.

## Модель стоимости

$$
T \approx T_0 + n_{br} \cdot p_{miss} \cdot C_{miss}, \qquad C_{miss} \approx 15 \ldots 20 \text{ тактов}
$$

## Классический эксперимент

```c
for (int i = 0; i < n; i++)
    if (a[i] < P)
        s += a[i];
```

`a[i]` - случайные числа от 0 до 99. Меняем порог `P` и меряем время на элемент:

<figure class="figure" markdown="1">
![Время суммы в зависимости от порога P](../images/branch-time-vs-p.svg#only-light){ width="720" }
![Время суммы в зависимости от порога P](../images/branch-time-vs-p.dark.svg#only-dark){ width="720" }
<figcaption>Сумма <code>a[i] &lt; P</code>: случайный массив, отсортированный массив и branchless-вариант. У случайного массива горб около P = 50-55, у отсортированного и branchless время почти не зависит от P.</figcaption>
</figure>

При `P = 0` и `P = 100` переход всегда в одну сторону - предсказатель не ошибается, и branchy-версия стоит около 0.2 нс на элемент. При `P = 50` ошибка в половине случаев, и время вырастает до 2.5-3 нс. Отсортированный массив дает монотонную последовательность переходов: предсказатель ошибается один раз, и горб исчезает.

В оригинальном эксперименте на массиве из $10^6$ элементов случайный порядок давал около 14 тактов на элемент, а отсортированный - около 4. На маленьком массиве (порядка 1000 элементов) предсказатель запоминает всю последовательность сравнений, и сортировка уже не нужна.

## Без ветвлений

```c
s += (a[i] < P) * a[i];            // арифметика
s += (a[i] < P) ? a[i] : 0;        // компилятор часто делает cmov
```

- x86: `cmov`, `setcc`. AArch64: `csel`.
- RISC-V: в базе условной пересылки нет; есть расширение Zicond (`czero.eqz`, `czero.nez`), иначе - арифметика с масками.
- Branchless всегда выполняет обе ветки. Выгодно, когда переход непредсказуем и ветки дешевые.

Predication можно записать формулой $x = c \cdot a + (1 - c) \cdot b$, где $c$ - результат сравнения, 0 или 1. Ветвление исчезает, но появляется зависимость по данным: `cmov` ждет флагов, зато не сбрасывает конвейер. Компиляторы выбирают `cmov`, когда вероятность перехода выше примерно 75%: при более предсказуемом переходе дешевле оставить ветку.

## Когда branchless проигрывает

Спекуляция - это не только риск, но и бесплатная предвыборка: процессор начинает грузить данные по угаданному пути заранее. В branchless-коде следующий адрес зависит от результата сравнения, и спекуляции нет.

Пример - бинарный поиск:

```c
const int *lower_bound_branchless(const int *base, int n, int x) {
    while (n > 1) {
        int half = n / 2;
        base += (base[half - 1] < x) * half;   // GCC и Clang делают cmov
        n -= half;
    }
    return base + (*base < x);
}
```

Тонкость: если записать тот же шаг как `base = (base[half - 1] < x) ? base + half : base`, Clang сделает `cmov`, а GCC 15 на `-O2` и `-O3` оставит обычный условный переход. Форма с умножением дает `cmov` у обоих. Код один и тот же по смыслу, а поведение конвейера - разное. Поэтому ассемблер проверяем всегда.

На маленьких массивах (в кэше) это в разы быстрее `std::lower_bound`. На больших - упирается в латентность памяти. Лечение: `__builtin_prefetch` обеих возможных следующих позиций или другая раскладка (Эйтцингер).

## Подсказки компилятору

`[[likely]]`, `[[unlikely]]`, `__builtin_expect` меняют раскладку кода (горячий путь идет без прыжка), но не учат предсказатель. Компилятор может сам превратить `if` в `cmov` - или наоборот. Всегда проверяйте ассемблер.

## Косвенные вызовы

Прямой вызов (`call f`) предсказывается легко: адрес записан в команде. Косвенный (`call *%rax`, `jalr`) зависит от значения регистра: указатель на функцию, виртуальный метод, `switch` на много веток. Процессор предсказывает адрес по истории (BTB - branch target buffer) и может ошибаться так же, как на обычном переходе.

Что важно:

- `switch` на много значений компилятор превращает в таблицу переходов или цепочку сравнений - смотрите ассемблер;
- виртуальные вызовы в C++ - это косвенный вызов через vtable; devirtualization (когда компилятор знает тип) убирает его;
- указатель на функцию в горячем цикле мешает и предсказанию, и инлайну.

## Раскладка кода

Скорость зависит не только от данных, но и от того, где лежит код:

- **front-end**: декодер читает код блоками; если горячий цикл не влезает в кэш инструкций, начинаются промахи I-cache;
- **выравнивание**: функция или цикл, пересекающий границу 32/64 байт, может декодироваться хуже; `-falign-functions`, `-falign-loops`;
- **неравные ветки**: горячий путь лучше держать без перехода, холодный - вынести в конец (`__builtin_expect`, `[[likely]]`);
- **hot/cold splitting**: холодный код компилятор выносит в отдельную секцию, чтобы он не занимал I-cache.

Это редкие, но реальные эффекты: иногда перестановка функций в файле меняет время на несколько процентов.

## Итоги

- Стоимость `if` зависит не от кода, а от предсказуемости данных.
- Branchless убирает переход, но выполняет обе ветки - выгодно, когда переход непредсказуем, а ветки дешевы.
- На больших массивах выигрыш съедает латентность памяти; спекуляция заодно работает предвыборкой.
- Что именно сделал компилятор, видно только в ассемблере.
