# 6. Конвейер, ILP и планирование

!!! warning "WIP"

Конвейер - главный трюк процессора: пока одна инструкция выполняется, следующая уже декодируется, а еще одна - читается из памяти. Он работает, пока инструкции независимы и поток предсказуем. Этот модуль - про то, что его ломает. ## Пять стадий

IF - выборка, ID - декодирование и чтение регистров, EX - АЛУ, MEM - доступ к памяти, WB - запись результата.

![Пять стадий конвейера](../images/pipeline-stages.svg#only-light){ width="720" }
![Пять стадий конвейера](../images/pipeline-stages.dark.svg#only-dark){ width="720" }
<figcaption>Пять стадий конвейера: к пятому такту в работе сразу пять инструкций. Цветом выделена стадия EX.</figcaption>
</figure>

Время на $n$ инструкций при $k$ стадиях длиной $\tau$:

$$
T_{pipe} = (k + n - 1)\,\tau, \qquad
S = \frac{n k \tau}{(k + n - 1)\tau} \xrightarrow[n \to \infty]{} k
$$

Латентность одной инструкции не уменьшается. Растет пропускная способность.

## Конфликты (hazards)

| Тип | Причина | Пример |
|---|---|---|
| структурный | два этапа хотят один ресурс | одна память для команд и данных |
| по данным | инструкции нужен результат предыдущей | `add x1,..` затем `sub x2, x1, ..` |
| по управлению | неизвестно, куда переход | `beq` в стадии ID/EX |

Цена у конфликтов разная. Структурный конфликт обычно стоит один такт ожидания свободного ресурса, и его нельзя убрать словами - только спроектировать код под доступные порты. Конфликт по данным стоит столько, сколько осталось до готовности операнда: это длина критического пути. Конфликт по управлению хуже всех: конвейер сбрасывается и теряет 15-20 тактов, поэтому переходы убирают или делают предсказуемыми.

## Цена конфликтов

$$
CPI = 1 + \frac{\text{stall-тактов}}{\text{инструкция}}
$$

Пример: 20% инструкций - переходы, 10% из них предсказаны неверно, штраф 15 тактов: $CPI = 1 + 0.2 \cdot 0.1 \cdot 15 = 1.3$.

У современных ядер 15-20 стадий и несколько инструкций за такт - штраф за неверное предсказание порядка 15-20 тактов, это десятки потерянных инструкций.

## Суперскалярность и внеочередное выполнение

Конвейер можно не только углубить, но и расширить: дублировать стадии и запускать за такт несколько инструкций. Процессоры, которые умеют больше одной инструкции за такт, называют **суперскалярными**, и почти все современные ядра такие. CPI у них может быть меньше единицы: например, 0.25 значит четыре инструкции за такт.

Расширение работает, только если в потоке есть независимые инструкции. Компилятор старается ставить их рядом, но порядок в программе все равно не идеален. Поэтому ядро держит буфер готовых к запуску операций и исполняет их **вне очереди** (out-of-order): как только операнды готовы и есть свободный исполнительный блок. Результат при этом выглядит так, как будто инструкции выполнены по порядку, - за это отвечает буфер переупорядочивания (ROB).

![Схема dual-issue процессора](../images/dual-issue.dark.svg#only-dark){ width="760" }
<figcaption>Dual-issue: общие стадии IF, ID и dispatch, два исполнительных блока EX0 и EX1, общие MEM и WB. Две независимые инструкции могут стартовать в одном такте.</figcaption>

Это похоже на университет: лекцию читают сразу потоку, а не каждому студенту отдельно (SIMD), занятия ведут несколько преподавателей параллельно (несколько исполнительных блоков), а курс повторяется для нового набора (конвейер). Пропускная способность растет, а время до диплома для одного студента - нет.

Ширина декодирования ограничивает, сколько инструкций ядро вообще может начать за такт. Внутри инструкции разбиваются на **микрооперации** (uOps), и каждая идет на свой **порт** - исполнительный блок с собственным маленьким конвейером. Планировщик держит буфер из сотен готовых операций и выбирает, что запустить, как только готовы операнды и свободен порт. Буфер большой, но не бесконечный: обращение к памяти с промахом кэша в него не помещается, и тогда внеочередное выполнение останавливается.

## Исключения и прерывания

- Исключение - синхронное (деление на ноль, page fault, `ecall`). Прерывание - асинхронное (таймер, устройство).
- Точные исключения: все инструкции до виновной завершены, после - нет. Конвейер для этого сбрасывается.

## Ввод-вывод: MMIO и DMA

- MMIO: регистры устройства отображены в адресное пространство. Чтение и запись - обычные `lw`/`sw`, в C - через `volatile`.
- Опрос (polling) против прерываний: опрос прост, но тратит процессор.
- DMA: контроллер сам копирует данные между устройством и памятью, процессор получает прерывание по окончании. Вопрос когерентности: кэш процессора может не знать, что DMA поменял память.

## Латентность и пропускная способность

- Латентность $L$: через сколько тактов готов результат.
- Обратная пропускная способность $\tau$: как часто можно запускать новую такую же независимую инструкцию.

Порядок величин для современных x86 (точные цифры - uops.info, Agner Fog):

| Инструкция | $L$, такты | $\tau$, такты |
|---|---|---|
| `mov r, r` | - | 0.25 |
| `mov r, m` | 4 | 0.5 |
| `mov m, r` | 3 | 1 |
| `add` | 1 | 0.25 |
| `cmp` | 1 | 0.25 |
| `popcnt` | 1 | 0.25 |
| `imul` | 3 | 1 |
| `div` | 13-28 | 13-28 |
| `addps`, `mulps`, `vfmadd` | 3-4 | 0.5 |
| `sqrtps` | 12-20 | 3-6 |

В таблицах обычно указывают **обратную пропускную способность** $\tau$: *больше* означает *хуже*. Если $\tau < 1$, у инструкции несколько исполнительных блоков, и за такт можно запустить больше одной. Нулевая латентность означает, что инструкция управляет планировщиком и до исполнения не доходит, но фронтенд ее все равно обрабатывает. У `div` латентность и $\tau$ совпадают: конвейера у деления почти нет.

## Цепочка зависимостей

```c
float s = 0;
for (int i = 0; i < n; i++) s += a[i];   // каждое сложение ждет предыдущее
```

Время: $n \cdot L_{add}$, ядро простаивает. Решение - несколько независимых аккумуляторов:

```c
float s0 = 0, s1 = 0, s2 = 0, s3 = 0;
for (int i = 0; i < n; i += 4) {
    s0 += a[i]; s1 += a[i + 1]; s2 += a[i + 2]; s3 += a[i + 3];
}
float s = (s0 + s1) + (s2 + s3);
```

Сколько нужно аккумуляторов? Закон Литтла: чтобы конвейер был полон, *в полете* должно быть

$$
k \ge \frac{L}{\tau}
$$

независимых операций. Для `addps`: $4 / 0.5 = 8$ аккумуляторов (и каждый - вектор, модули 15-16).

Компилятор сам так не сделает для `float`: это меняет порядок сложений (модуль 4). Для целых - сделает.

## Пример: полином

$$
p(x) = a_0 + a_1 x + a_2 x^2 + \dots + a_n x^n
$$

Схема Горнера: $p = a_0 + x(a_1 + x(a_2 + \dots))$ - минимум операций, но цепочка из $n$ FMA, время одного значения $n \cdot L_{fma}$.

Схема Эстрина: группируем попарно,

$$
p(x) = (a_0 + a_1 x) + x^2 (a_2 + a_3 x) + x^4 \bigl( (a_4 + a_5 x) + x^2 (a_6 + a_7 x) \bigr) + \dots
$$

Операций чуть больше, но глубина цепочки $O(\log n)$. Если считаем полином для массива точек, независимые $x_i$ тоже дают ILP: можно обрабатывать несколько точек за раз.

## Теоретический предел

Пиковая производительность одного ядра:

$$
P_{peak} = f \cdot (\text{FMA-блоков}) \cdot (\text{полос в векторе}) \cdot 2
$$

Пример: 3 ГГц, 2 FMA-блока, AVX2 (8 float): $3 \cdot 2 \cdot 8 \cdot 2 = 96$ GFLOPS. Если ваш код получает 2 GFLOPS - есть куда расти.

На практике предел задает не только арифметика. Ширина декодирования ограничивает число инструкций за такт; порты - число одновременных операций каждого типа; память - пропускную способность и латентность. Например, инкремент массива `vpaddd` + `vmovdqa` упирается в порт записи, а не в АЛУ: восемь значений за такт при 2 ГГц дают около 16 GFLOPS. Поэтому прежде чем считать *пик*, найдите, какой ресурс действительно загружен.

## Итоги

- Конвейер повышает пропускную способность, а не уменьшает латентность одной инструкции: $T_{pipe} = (k + n - 1)\tau$.
- Конфликты по данным снимаются forwarding, кроме load-use, где нужен пузырь; компилятор переставляет инструкции, чтобы его не было.
- Цена неверного предсказания - 15-20 тактов, то есть десятки выброшенных инструкций.
- Исключения и прерывания требуют точного состояния; MMIO и DMA показывают, что ввод-вывод - это тоже память.
- У инструкции две характеристики: латентность $L$ и пропускная способность $\tau$.
- Цепочка зависимостей ограничивает параллелизм: ускорение не больше $L / \tau$.
- Несколько аккумуляторов и схема Эстрина укорачивают цепочки, не меняя число операций.
- Производительность цикла ограничена не числом инструкций, а длиной цепочек зависимостей и пропускной способностью портов.
- Модель `llvm-mca` полезна, но окончательный ответ дает замер.
