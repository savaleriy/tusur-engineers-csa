# 8. Компилятор: флаги, UB и контракты

!!! warning "WIP"
    Материал в работе: текст и задания могут меняться.

Компилятор - главный оптимизатор в вашей жизни. Он делает огромную работу, но только ту, которую может доказать. Наша задача - понимать, что ему мешает, как дать ему больше информации и когда (редко) нужно писать ассемблер самим.

```bash
gcc -E f.c        # после препроцессора
gcc -S -O2 f.c    # ассемблер
gcc -c f.c        # объектный файл
gcc -save-temps -O2 f.c   # все промежуточные файлы
```

Файлы собираются по отдельности, а потом компонуются: так сборку можно распараллелить и кэшировать. Библиотеки бывают статическими (объектные файлы вливаются в бинарник) и разделяемыми (код подключается во время запуска). Статическая библиотека дает компилятору больше контекста для межпроцедурных оптимизаций; современный способ сохранить это преимущество при раздельной сборке - **LTO** (link-time optimization), когда в объектных файлах хранится IR. Флаг `-fverbose-asm` добавляет в ассемблер комментарии с номерами строк и переменными.

## Уровни и цели

| Флаг | Что дает |
|---|---|
| `-O0` | без оптимизаций, удобно отлаживать |
| `-O1` | базовые оптимизации |
| `-O2` | почти все безопасные; в GCC 12+ включена *дешевая* векторизация |
| `-O3` | агрессивное встраивание, развертка, векторизация |
| `-Os` | размер кода |
| `-Ofast` | `-O3` + `-ffast-math` (нарушает IEEE 754) |
| `-march=X` | разрешить инструкции процессора X (бинарник может не запуститься на другом) |
| `-mtune=X` | планировать под X, но только базовыми инструкциями |
| `-march=native` | все расширения текущей машины |

RISC-V: `-march=rv64gcv_zba_zbb -mabi=lp64d`.

`-O2` - обычный выбор для продакшена, `-O3` включает агрессивное встраивание и развертку, `-Ofast` добавляет `-ffast-math` и разрешает нарушать IEEE 754. `-march=x` разрешает инструкции конкретного процессора, `-mtune=x` только планирует под него, не используя новых инструкций; `-march=native` определяет текущую машину. Для отдельной функции флаги можно задать прагмами `#pragma GCC optimize` и `#pragma GCC target`, а несколько реализаций одной функции - атрибутами `target` (multiversioned functions).

## Что компилятор делает сам

Встраивание, свертка констант, вынос инвариантов из цикла, удаление мертвого кода, замена деления на константу умножением, развертка циклов, векторизация, превращение хвостовой рекурсии в цикл.


## Что ему мешает

- Алиасинг: указатели могут указывать на одну память.

```c
void add(float *a, const float *b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];   // а если b == a + 1?
}
```

Компилятор либо не векторизует, либо вставит проверку во время выполнения и сделает две версии цикла: для пересекающихся и для непересекающихся указателей. Подсказка: `float *__restrict a`. - Порядок операций с плавающей точкой (нужен `-ffast-math` или `-fassociative-math`, см. модуль 4). - Вызовы внешних функций, которые нельзя встроить. - Неизвестное число итераций, сложный поток управления.

## Неопределенное поведение

UB - не *ошибка, которая упадет*. Это обещание программиста компилятору: *такого не бывает*. Компилятор этим пользуется.

UB существует по двум причинам. Первая - ошибки, которые почти наверняка непреднамеренны: деление на ноль, разыменование NULL, чтение неинициализированной памяти. Их лучше поймать санитайзером, чем получить молчаливый неверный результат. Вторая - операции, которые на разных платформах ведут себя по-разному, например сдвиг на ширину типа или знаковое переполнение. Если зафиксировать одно поведение, другая платформа заплатит за проверку в каждом таком месте. Поэтому стандарт оставляет поведение неопределенным, а компилятор получает право считать, что *такого не бывает*.

```c
int f(int x) { return x + 1 > x; }      // -> return 1;  (знаковое переполнение - UB)

int g(int *p) {
    int v = *p;                         // разыменовали - значит p != NULL
    if (p == NULL) return 0;            // проверку можно удалить
    return v;
}
```

Типичные UB: знаковое переполнение, выход за границы массива, разыменование NULL, нарушение strict aliasing, сдвиг на ширину типа и больше, неинициализированные переменные.

Ловим: `-fsanitize=undefined,address`, `-Wall -Wextra`.

## Контракты: как дать компилятору информацию

| Средство | Что сообщает |
|---|---|
| `__restrict` | указатели не пересекаются |
| `__builtin_assume_aligned(p, 32)` | адрес выровнен |
| `__builtin_unreachable()`, `[[assume(x)]]` (C++23) | условие всегда истинно |
| `__builtin_expect(x, 1)`, `[[likely]]` | какая ветка чаще |
| `constexpr`, `static` | вычисли при компиляции, функция не видна снаружи |

Ошибка в контракте - тоже UB.

## Inline asm

```c
asm volatile ("инструкции" : выходы : входы : испорченное);
```

| Элемент | Значение |
|---|---|
| `"=r"(x)` | выход в любом регистре |
| `"+r"(x)` | вход и выход |
| `"r"(y)`, `"m"(z)`, `"i"(5)` | вход: регистр, память, константа |
| `"memory"` | asm читает или пишет память |
| `"cc"` | asm портит флаги (x86) |
| `volatile` | не удалять и не переносить |

Примеры:

```c
static inline uint64_t rdtsc(void) {            // x86-64
    uint32_t lo, hi;
    __asm__ volatile ("rdtsc" : "=a"(lo), "=d"(hi));
    return ((uint64_t)hi << 32) | lo;
}

static inline uint64_t rdtime(void) {           // RISC-V
    uint64_t t;
    __asm__ volatile ("rdtime %0" : "=r"(t));
    return t;
}
```

Когда inline asm нужен: доступ к инструкциям без C-аналога (счетчики, CSR, барьеры), микробенчмарки инструкций (задание 6), защита от оптимизаций. Когда не нужен: почти всегда для вычислений. Интринсики лучше: компилятор сам распределяет регистры и оптимизирует вокруг. Asm для него - черный ящик.

## Итоги

- Компилятор оптимизирует только то, что может доказать; недоказанное оставляет как написано.
- Неопределенное поведение - это разрешение выбросить код целиком, а не мелкая придирка.
- Контракты (`restrict`, `assume`, выравнивание) расширяют то, что компилятор имеет право предположить.
- Inline asm - последний инструмент, когда язык не выражает нужное.
