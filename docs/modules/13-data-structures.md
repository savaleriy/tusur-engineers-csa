До сих пор мы ускоряли код, меняя порядок циклов, раскладку и векторы. Но самый большой выигрыш часто дает не арифметика, а **структура данных**: как разложены элементы в памяти и сколько промахов стоит один запрос. Иногда бинарное дерево на указателях проигрывает массиву в десять раз при той же асимптотике $O(\log n)$.

## Бинарный поиск

Начнем с задачи, которую все знают: найти `x` в отсортированном массиве.

```c
const int *lower_bound(const int *a, int n, int x) {
    while (n > 1) {
        int half = n / 2;
        a += (a[half - 1] < x) * half;
        n -= half;
    }
    return a + (*a < x);
}
```

Здесь нет ветвления: сравнение превращается в 0 или 1 и умножается на половину. Но главная проблема не в переходе, а в памяти: каждое следующее обращение идет в случайное место массива, и на больших $n$ это промах кэша на каждом шаге.

Что с этим делать:

- **индексы вместо указателей** - меньше зависимостей и лучше предвыборка;
- **branchless-вариант** - убирает неверные предсказания, но не промахи;
- **раскладка Eytzinger** - дерево, уложенное в массив так, что поиск идет по уровням, а не по случайным адресам;
- **B-дерево** - несколько ключей в одном узле, чтобы одно обращение к памяти окупало больше сравнений.

## Раскладка Eytzinger

Eytzinger-раскладка - это дерево поиска, записанное в массив в порядке обхода в ширину:

```text
дерево:        4
             /   \
            2     6
           / \   / \
          1   3 5   7

массив:  [4, 2, 6, 1, 3, 5, 7]
индексы:  1  2  3  4  5  6  7
```

Корень в `a[1]`, дети узла `i` - в `a[2i]` и `a[2i+1]`. Поиск:

```c
int search_eytzinger(const int *a, int n, int x) {
    int k = 1;
    while (k <= n)
        k = 2 * k + (a[k] < x);
    k >>= 1;
    return k;
}
```

Ветвление здесь тоже можно убрать, но главное - обращения идут последовательно по уровням, и аппаратный префетчер успевает подтягивать следующие узлы.

## Статическое B-дерево

Если массив не меняется, можно хранить не двоичное дерево, а B-дерево: в одном узле 16-32 ключа, и одно обращение к памяти сразу сравнивает много ключей.

```text
узел: [ 4 | 8 | 12 | 16 | 20 | 24 | 28 | 32 ]
       /   |   |    |    |    |    |    |   \
    <4   4-8 8-12 ...                      >32
```

Поиск в узле - бинарный или SIMD-сравнением; переходов становится меньше, а кэш-линий на запрос - тоже. Для статических данных это часто быстрее и Eytzinger, и `std::lower_bound`.

## Хеш-таблицы

Хеш-таблица тоже упирается в память. Два классических варианта:

- **цепочки** (chaining): массив голов списков; каждая вставка - переход по указателю, плохо для кэша;
- **открытая адресация** (open addressing): все элементы в одном массиве, коллизии разрешаются пробами; лучше для кэша, но требует контроля заполнения.

```c
struct entry { uint64_t key; uint32_t value; };
/* линейное пробирование */
size_t i = hash(key) & mask;
while (table[i].key != EMPTY && table[i].key != key)
    i = (i + 1) & mask;
```

Что важно:

- степень заполнения: при 70-80% пробы растут, при 90% - резко;
- удаление: либо `tombstone`, либо перестройка;
- хеш-функция: быстрая и с хорошим перемешиванием (см. модуль 17);
- ключ и значение в одной линии - меньше промахов.

## Сортировка

Сортировка - хороший тест на понимание памяти: алгоритмы с одинаковой асимптотикой $O(n \log n)$ могут отличаться в разы.

- **Quicksort** ($O(n \log n)$ в среднем) хорошо работает на массивах, но ветвится и плохо предсказуем; `qsort`/`std::sort` - разумный выбор по умолчанию.
- **Radix sort** сортирует целые по байтам: 4 прохода по 8 бит для `uint32_t`, на каждом - подсчет и устойчивая перестановка. Время $O(n)$ при фиксированном числе бит, но нужен второй массив.
- **Сортирующие сети** (bitonic, odd-even) не ветвятся: сравнение и перестановка через `min`/`max`, компилятор делает `cmov`. Хороши для маленьких фиксированных размеров и SIMD.

```c
/* LSD radix sort по байтам; нужен <stdlib.h> и <string.h> */
void radix_sort_u32(uint32_t *a, size_t n) {
    uint32_t *tmp = malloc(n * sizeof *tmp);
    if (!tmp) return;
    for (int shift = 0; shift < 32; shift += 8) {
        size_t cnt[256] = {0}, pos[256];
        for (size_t i = 0; i < n; i++) cnt[(a[i] >> shift) & 255]++;
        pos[0] = 0;
        for (int b = 1; b < 256; b++) pos[b] = pos[b - 1] + cnt[b - 1];
        for (size_t i = 0; i < n; i++)
            tmp[pos[(a[i] >> shift) & 255]++] = a[i];
        memcpy(a, tmp, n * sizeof *a);
    }
    free(tmp);
}
```

На $10^7$ случайных `uint32_t` radix обычно обгоняет `qsort` в 2-4 раза; сортирующая сеть на 16 элементах - в разы быстрее вставок. Проверьте на своей машине: все зависит от того, помещается ли массив в кэш.

## Графы и CSR

Граф - это вершины и ребра; способ хранения решает, сколько будет промахов кэша.

- **Матрица смежности** $n \times n$: $O(1)$ проверка ребра, но $O(n^2)$ памяти.
- **Списки смежности** на указателях: память $O(n+m)$, но каждый список - отдельные узлы и pointer chasing.
- **CSR** (compressed sparse row): два массива - `offset[n+1]` и `edges[m]`; соседи вершины $v$ лежат в `edges[offset[v]..offset[v+1])` подряд. Память $O(n+m)$, обход последовательный.

```c
/* BFS по CSR; dist инициализирован -1 */
void bfs(const size_t *offset, const uint32_t *edges,
         size_t n, uint32_t src, int *dist) {
    for (size_t i = 0; i < n; i++) dist[i] = -1;
    uint32_t *q = malloc(n * sizeof *q);
    size_t head = 0, tail = 0;
    dist[src] = 0; q[tail++] = src;
    while (head < tail) {
        uint32_t v = q[head++];
        for (size_t e = offset[v]; e < offset[v + 1]; e++) {
            uint32_t u = edges[e];
            if (dist[u] < 0) { dist[u] = dist[v] + 1; q[tail++] = u; }
        }
    }
    free(q);
}
```

BFS обходит каждое ребро один раз, но на больших графах упирается в память: вершины и ребра разбросаны. CSR дает последовательный обход соседей, поэтому на практике бывает в разы быстрее списков на указателях.

Есть и direction-optimizing BFS: на плотных фронтах выгоднее идти по входящим ребрам, а не по исходящим.

## Что мерить

Для любой структуры данных нас интересуют:

- наносекунды на запрос при разных $n$ (от L1 до DRAM);
- `cache-misses` и `branch-misses` на запрос;
- сколько линий кэша читается на один запрос.

Постройте график "нс на запрос от $n$" для `std::lower_bound`, branchless-версии, Eytzinger и B-дерева - и увидите, где какая структура выигрывает.

## Итоги

- Асимптотика не говорит, сколько стоит запрос: важна раскладка в памяти.
- Eytzinger и B-дерево меняют число промахов, а не число сравнений.
- Открытая адресация обычно быстрее цепочек за счет локальности.
- Любую структуру данных надо мерить на своих размерах, а не выбирать по вкусу.
- Radix sort дает $O(n)$ для целых фиксированной ширины, но требует второй массив; сортирующие сети убирают ветвления.
- CSR делает обход графа последовательным; списки на указателях проигрывают на больших графах из-за промахов.
