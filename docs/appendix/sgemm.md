# SGEMM: от naive до OpenMP

!!! note "К модулю 19"
    Это практическое дополнение к модулю 19. Полный код лежит в папке `examples/sgemm` репозитория курса; здесь - схема пути и объяснение, зачем нужен каждый шаг.

## Зачем отдельный разбор

Умножение матриц - удобный полигон: формула одна, а скорость меняется в десятки раз. В naive-версии время уходит на память; в хорошей версии - на FMA и регистры. Ниже пять стадий: naive, блочность, упаковка, микроядро и OpenMP. MPI добавляется шестым шагом, когда одного узла уже мало.

## Стадии

| Стадия | Что добавлено | Что обычно ускоряет |
|---|---|---|
| `naive` | три цикла | ничего, это база |
| `cache` | блоки `MC/NC/KC`, упаковка панелей | кэш L1/L2/L3 |
| `pad` | дополнение крайних блоков нулями | убирает отдельный код для краев |
| `micro` | микроядро 16x6, 12 аккумуляторов | FMA и регистры |
| `parallel` | OpenMP по блокам столбцов | ядра одного узла |
| MPI | блоки строк по рангам | несколько узлов |

## Обозначения

Матрицы хранятся по столбцам, как в BLAS: элемент `(i, j)` матрицы `C` лежит в `C[j * M + i]`. Для `A` шаг строки равен `M`, для `B` - `K`, для `C` - `M`. В тексте `M x K` - размер `A`, `K x N` - размер `B`, `M x N` - размер `C`.

$$
C_{ij} = \sum_{p=0}^{K-1} A_{ip} B_{pj}
$$

## Шаг 0. Naive

Три цикла в порядке `i-j-p` читают `B` с шагом в строку: каждый следующий элемент `B[p][j]` находится далеко от предыдущего. Процессор ждет память, а не считает. Арифметическая интенсивность при этом падает: данные не переиспользуются из кэша.

Простая перестановка циклов в `i-p-j` уже помогает: `A[i][p]` читается один раз, а `B[p][j]` идет подряд по `j`. Это еще не блочность, но первая причина, почему порядок циклов вообще важен.

## Шаг 1. Блоки и упаковка

Матрицы режутся на блоки под три уровня кэша. Внешний цикл `jc` идет по столбцам `C`, затем `pc` по `K`, затем `ic` по строкам `M`. Внутри - микротайлы `MR x NR`.

![Блоки GEMM и упаковка панелей](../images/gemm-blocking.dark.svg#only-dark){ width="820" }
<figcaption>Три уровня блоков: панель B под L3/L2, панель A под L2, микротайл C под L1 и регистры.</figcaption>
</figure>

Панель `B` размера `KC x NC` упаковывается в непрерывный буфер: элементы, которые микроядро будет читать вместе, лежат рядом. Панель `A` размера `MC x KC` упаковывается так же. Упаковка стоит времени, но она окупается: каждое обращение к памяти теперь приносит данные, которые реально используются.

Крайние блоки, у которых `mc < MC` или `nc < NC`, дополняются нулями. Тогда микроядро всегда работает с полным блоком `MR x NR` и не содержит отдельной ветки для каждого края. Нули не меняют результат, но требуют аккуратной записи только в допустимые элементы `C`.

## Шаг 2. Микроядро

Микроядро держит блок `C` в регистрах. Для `MR = 16` и `NR = 6` это 12 регистров `ymm`: по два вектора на каждый из шести столбцов. Еще два регистра заняты вектором `A`, один - очередным скаляром `B`. Итого 15 из 16 регистров `ymm`.

<figure class="figure" markdown="1">
![Микроядро 16x6](../images/gemm-microkernel.svg#only-light){ width="760" }
![Микроядро 16x6](../images/gemm-microkernel.dark.svg#only-dark){ width="760" }
<figcaption>Микроядро 16x6: 12 аккумуляторов C, две загрузки A и шесть broadcast B на каждый шаг k.</figcaption>
</figure>

На каждом шаге `k` микроядро делает две загрузки `A`, шесть broadcast `B` и 12 FMA. Это 12 умножений-сложений на 2 загрузки и 6 broadcast, то есть арифметика начинает доминировать над памятью. Именно ради этого отношения и нужны упаковка и блочность.

Если `mr < 16` или `nr < 6`, крайние векторы маскируются. Маска позволяет не читать и не писать за границей матрицы; вместо отдельного медленного пути для каждого края остается тот же микроядро с маской.

## Шаг 3. OpenMP

OpenMP делит работу внутри одного процесса. В `matmul_parallel` параллелится внешний цикл по блокам столбцов `jr`: каждый поток получает свой набор столбцов `C` и пишет только в них. Панель `B` при этом общая и только читается, а панель `A` у каждого потока своя.

<figure class="figure" markdown="1">
![OpenMP и MPI для GEMM](../images/gemm-parallel.svg#only-light){ width="820" }
![OpenMP и MPI для GEMM](../images/gemm-parallel.dark.svg#only-dark){ width="820" }
<figcaption>Слева OpenMP делит столбцы C между потоками; справа MPI делит строки C между рангами.</figcaption>
</figure>

Ложного разделения здесь нет: блоки `C` у потоков не пересекаются, а общая панель `B` не меняется. Если параллелить внутренний цикл по `ir`, потоки начнут писать в соседние элементы одной кэш-линии и получат ложное разделение. Поэтому важен именно внешний блок.

Статическое расписание хорошо для одинаковых блоков. Динамическое нужно, когда блоки разные или ядра неравные, как P/E-ядра на некоторых процессорах. Число потоков задается при сборке `NTHREADS`; для графика ускорения собирают несколько бинарников и считают время на одном и том же `n`.

Ускорение ограничено законом Амдала: последовательная часть - упаковка, запуск, синхронизация - не исчезает. Поэтому на 8 потоках редко видно ровно 8x; полезно измерять не только GFLOPS, но и долю времени вне микроядра.

## Шаг 4. MPI

MPI нужен, когда матрица не помещается в память одного узла или одного узла не хватает по ядрам. Простейшая схема - делить строки `C` между рангами:

1. Ранг `r` получает свою полосу строк `A` и хранит ее локально.
2. Панель `B` нужна всем; ее рассылают через `MPI_Bcast` или делят по `k` и собирают частичные суммы.
3. Каждый ранг считает свою полосу `C`.
4. Полосы собираются через `MPI_Gatherv`; если результат нужен всем, используют `MPI_Allgatherv`.

У GEMM высокая арифметическая интенсивность, поэтому передача панели `B` окупается на больших `n`. На малых `n` время на коммуникации и запуск съест весь выигрыш. Для многих узлов используют двумерное разбиение и алгоритмы вроде SUMMA, где панели передаются по кольцу, а не рассылаются всем сразу.

В текущем `examples/sgemm` MPI-кода нет: это следующий шаг после OpenMP. Но структура блоков уже готова: те же панели `A` и `B` и те же микротайлы, только цикл по строкам распределяется между рангами. Для будущих экспериментов понадобятся пакеты `openmpi-bin` и `libopenmpi-dev`.

## Как запускать

Нужны AVX2, FMA и OpenMP:

```bash
sudo apt install -y build-essential libomp-dev
cd examples/sgemm
make
./runner-naive    1000 1000 1000 5
./runner-cache    1000 1000 1000 5
./runner-pad      1000 1000 1000 5
./runner-micro    1000 1000 1000 5
./runner-parallel 1000 1000 1000 5
```

Пять строк `Exec. time` и `GFLOPS` - пять запусков. Проверка корректности:

```bash
gcc -O3 -mavx2 -mfma -fopenmp -mno-avx512f -DNTHREADS=4 -DTEST \
    -DMATMUL_VER=matmul_pad runner.c -o runner-pad-test
./runner-pad-test 1000 1000 1000 1
```

Ожидаемо `PASSED!`. Эталон - `matmul_naive`, допуск `1e-4`.

## Как измерять

Для каждой стадии и каждого `n` нужно не меньше пяти запусков, медиана и разброс. Один запуск ничего не доказывает: планировщик, турбо-частота и соседние процессы дают разброс больше, чем разница между некоторыми стадиями.

Считайте `GFLOPS = 2 n^3 / (t * 10^9)` и сравнивайте с пиком ядра из модуля 19. На графике `GFLOPS` от `n` видно, где версия упирается в память, а где подходит к горизонтальной части roofline. Полезно добавить `perf stat`: для naive растут cache-misses, для микроядра - нет.

## Что должно получиться

Порядок стадий на x86-64 с AVX2 обычно такой: `naive` заметно медленнее всех, `cache` и `pad` дают кратный рост, `micro` добавляет FMA и регистры, `parallel` масштабируется по ядрам. Конкретные числа зависят от CPU, памяти, компилятора и размера `n`; их нельзя переносить с одной машины на другую.

На малых `n` параллельная версия может проигрывать однопоточной: накладные расходы OpenMP больше работы. Это нормальный результат, его нужно объяснить, а не прятать.
